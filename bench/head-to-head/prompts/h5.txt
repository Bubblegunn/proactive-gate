We want to know how a week of past notifications would have looked under a new policy before we ship it. Write bot.mjs in the current folder (Node 22, ES module; if you need a dependency, add it to package.json and install it) that exports `function replay({ events, policy })` and `function compare({ events, policyA, policyB })`. An event is `{ id, userId, timezone, at, priority }` where `at` is an ISO 8601 UTC string, `timezone` is an IANA name, and priority is "normal" or "critical". A policy is `{ quietHours: { start: "HH:MM", end: "HH:MM" } | null, dailyCap: number | null }`; quiet hours are in the user's local time and may cross midnight, and a "critical" event ignores quiet hours but still counts against the cap and is still refused when the cap is full. `replay` processes the events in time order (ties keep the input order; the input array may be in any order and must not be modified), each event once, and returns `{ decisions, counts }`. `decisions` is an array in that processing order of `{ id, outcome, holdUntil, reason }`: outcome "sent" (holdUntil null, reason null) when the event may go out and then counts against its user's cap for the user's local calendar day; "held" when quiet hours stop it, with `holdUntil` the ISO UTC string of the moment quiet hours end for that user and a reason sentence containing "quiet hours"; "refused" when the cap for that local day is already used up, with holdUntil null and a reason sentence containing "daily cap". Quiet hours are checked first; a held or refused event consumes nothing and is not retried. `counts` is `{ sent, held, refused }`. `compare` replays the same events under both policies and returns `{ countsA, countsB, changed }`, where `changed` lists, in processing order, `{ id, from, to }` for every event whose outcome differs, using the outcome names. Do not touch the network or any file; this is pure computation. Check that it works before you finish.
