# proactive-gate

Put a gate in front of every message your agent sends on its own initiative. The gate decides whether a message may go now and never sends anything. A refusal names the check, says why, and gives the earliest retry time when there is one.

## When to use it

- You are adding a reminder, nudge, digest, alert or follow-up the user did not just ask for.
- The user asks for quiet hours, a message limit, a pause, consent checks or opt-out handling.
- The message leaves from a loop, a schedule or a webhook, not as the answer to something the user just wrote.

## Default: write the gate inline

Write the gate in ONE file, the file the task names. No install, no scaffold, no reading of library source, no separate test file. Write the file, append the kit (below) and run one self-check in one shell command (heredoc and `node -e`), then answer. Aim at 4 turns after this skill loads; the self-check covers rules 3 to 6, and your answer says which rule it did not check. The gate must follow these rules:

1. Data. Use only the fields the task or the app gives. Never invent a field, a key or a purpose name. A missing field is unknown, not "no".
2. Consent. When the data carries a consent field, false or absent means off. When it carries none: (a) a message the user signed up for or asked for (digest, briefing, reminder) is allowed; (b) a newsletter or other email or in-app message to people the request calls subscribers, customers or list members is allowed unless an opt-out is recorded for that user and channel (a true opt-out field, or a STATE_DIR record, rule 7; an opt-out field the data carries but leaves missing is unknown, so hold); (c) a promotion by text, call or autodialer needs an explicit opt-in in the data, whatever the request calls the people; (d) any other promotion and any other unknown case is held. Exception: when the request's functions can record only opt-outs (unsubscribe, STOP) and no opt-in, a missing opt-in never holds an email or in-app message and never lifts (c); allow it and say so in one sentence in your answer.
3. Never hold everything. Before you finish, call the exported function with exactly the fields the task lists and confirm that one message is allowed.
4. State. Read STATE_DIR inside every call, not at import and not once and cached. Create it. Keep one record per user and per message id. Every worker process shares it and it survives a restart. Write with an atomic step (the kit's `gkWrite(dir, key, obj)`, `gkClaim(dir, key)`, `gkCount(dir, key, limit)`) so two workers cannot both win.
5. Redelivery. Key every send by message id: the same id gets the same answer and spends nothing twice. Claim before sending. Give the claim back only when the send definitely did not happen (the gate refused it, or it failed before leaving). When the outcome is unknown, keep the claim. A suppression such as "this key was already shown" lasts until the end of the recipient's local day unless the request says longer.
6. Time. Use the recipient's local time (the device zone first when the data has one). An unknown or invalid zone is held, never guessed. A window includes its start minute and excludes its end minute, across DST; a start later than the end wraps past midnight. A local day, week or month is the recipient's own. Use the kit for all of it. A window the request states is the window; never narrow it and never add one the request does not state, except the law the request names (for example the US calling hours, 08:00 to before 21:00 recipient-local, for promotional texts and calls when the request names that law). A hold from a window, quiet hours or a cap stops the interrupting surface (push, SMS, call); a silent in-app or feed item for the same message is still produced when the app has one.
7. Opt-out. Match STOP, STOPALL, UNSUBSCRIBE, CANCEL, END, QUIT, REVOKE, OPT OUT, OPT-OUT and OPTOUT as the whole message, any case, outer punctuation and extra spaces ignored (`gkIsStop(text)`); "stopping" is not STOP. Opt-out is per channel, holds in every process at once and beats every other rule for unsolicited and promotional messages. It acts on the opt-out the data carries (a field or an inbound STOP), never on whether the outgoing message body holds an opt-out notice. START or UNSTOP turns it back on (`gkIsStart(text)`). The account-page opt-out writes the same record.
8. Refusals. Return a plain sentence that names the rule. When there is a retry time, write it as the recipient's local clock time with the zone name (`gkFmt(instant, zone)`), never as an ISO string or only "UTC", and return the same instant in its own field (for example nextAllowedAt). Never a bare internal code.
9. Time-critical messages. Something the user asked to be told at a time may use a reserved budget. Opt-out, quiet hours and legal hours still apply to it. Transactional exception: a transactional message (receipt, security code, courier) that the request says must still reach the person and carries no promotion is not held by quiet hours or a marketing cap and does not count toward it; its channel's opt-out (rule 7) still applies. A message held for any reason spends no budget.
10. Numbers you chose (hours, caps, cooldowns) go in your answer, one line each.
11. Blocks. Rules 1 to 10 always apply (consent, opt-out, recipient-local legal and quiet hours, a valid zone, the caps). Add no other block unless the request states it, or a law or policy text it names requires it of the sender before sending. A check on the outgoing message body (a required notice, a word, a length) is a recommendation unless the request or a named law requires it: allow the message and write "not enforced: (the check)" in your answer; when unsure, do not block. Consent (rule 2) and opt-out (rule 7) are not new blocks: when unsure whether consent is present, hold, except under the opt-in exception of rule 2.

## The kit

`references/gate-kit.mjs` holds tested functions for local time, windows, day keys, STOP words and shared state. For an ESM file (.mjs, or .js in a "type": "module" project) append it to your file in the same shell command that writes the file: `cat "${CLAUDE_SKILL_DIR}/references/gate-kit.mjs" >> bot.mjs`. Do not retype it. Times are epoch milliseconds (`date.getTime()`), zones IANA names.
`gkZoneOk(zone)`, `gkLocal(ms, zone)`, `gkInWindow(ms, zone, "08:00", "21:00")`, `gkNextOpen(ms, zone, start, end)` (earliest instant inside the window: the retry time; for quiet hours pass the quiet end as start and the quiet start as end), `gkDayKey(ms, zone)`, `gkWeekKey(ms, zone)`, `gkMonthKey(ms, zone)`, `gkNextMidnight(ms, zone)`, `gkFmt(ms, zone)`, `gkIsStop(text)`, `gkIsStart(text)`, `gkClaim(dir, key)`, `gkUnclaim(dir, key)`, `gkCount(dir, key, limit)` (atomic, returns {ok, n}), `gkRefund(dir, key)`, `gkRead(dir, key)`, `gkWrite(dir, key, obj)`. For TypeScript or CommonJS write the same logic by hand under the rules above.

## Use the library instead when

The project already imports proactive-gate, or the user asks for a policy file, a scaffold, a log of why a user got nothing, or replay. Run `node -v` first: it must print 22 or newer (npm on an older Node installs proactive-gate 0.7.3, an older API, without a warning). Then run `npx proactive-gate scaffold nudge --out .` (add `--legal us` for texts to people in the US). Mark a candidate `requested`, `transactional` or kind "commitment" when it is one, and never mark a promotion that way. Set STATE_DIR for state that outlives the process. Call `gate.record` on every "acted" and "dismissed" event so the cooldown learns, and pass `deviceTimezone` when the device reports one. Change `toInput()` in `notify.mjs` to the app's shapes and run `node --test notify.test.mjs` before `decide()` or `deliver()` goes into a send path.
notify.mjs exports decide (send, reason, reasonCode, surfaces), deliver (calls the app's push and inApp, returns push, inApp, reason, resumeAt), recordDismissal, recordAct and optOut (a type or a channel).
It also exports handleInbound, whyNotReceived (one user's log over a time range), dryRun (last week under another policy) and REASON_CODES, the closed list of reasonCode values.

- `references/guide.md`: the policy format, the decision loop, stores, inbound STOP and START, legal presets and replay.
- `references/checks.md`: one line per check id, the gate functions, and the `assistantNudge` preset.
