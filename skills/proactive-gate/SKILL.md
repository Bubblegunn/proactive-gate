# proactive-gate

Put a gate in front of every message your agent sends on its own initiative. The gate decides whether a message may go now and never sends anything. A refusal names the check, says why, and gives the earliest retry time when there is one.

## When to use it

- You are adding a reminder, nudge, digest, alert or follow-up the user did not just ask for.
- The user asks for quiet hours, a message limit, a pause, consent checks or opt-out handling.
- The message leaves from a loop, a schedule or a webhook, not as the answer to something the user just wrote.

## Default: write the gate inline

Write the gate in ONE file, the file the task names. No install, no scaffold, no reading of library source, no separate test file. Write the file with a heredoc, append the kit (below) and run one self-check in the same shell command, then answer; change the file afterwards only with Edit, never Write. Aim at 4 turns after this skill loads; the self-check covers rules 3 to 6, and your answer says which rule it did not check. The gate must follow these rules:

1. Data. Use only the fields the task or the app gives. Never invent a field, a key or a purpose name. A missing field is unknown, not "no".
2. Consent. When the data carries a consent field, false or absent means off; any field where the person chose what to receive (consent, categories, preferences, a notification permission) is one, and with it off or missing the push is off, though a silent in-app item may still be produced (rule 6). When it carries none: (a) a message the user signed up for or asked for (digest, briefing, reminder) is allowed; (b) a newsletter or other email or in-app message to people the request calls subscribers, customers or list members is allowed unless an opt-out is recorded for that user and channel (a true opt-out field, or a STATE_DIR record, rule 7; an opt-out field the data carries but leaves missing is unknown, so hold); (c) a promotion by text, call or autodialer needs an explicit opt-in in the data, whatever the request calls the people; (d) any other promotion and any other unknown case is held. Exception, with no consent field: when neither the data nor the functions the request or the app exposes can carry an opt-in (they record only opt-outs, or nothing), a missing opt-in holds nothing, not even under (c) or (d), because the check could only hold every message; allow when no opt-out is recorded for that user and channel, and write "not enforced: opt-in (the interface carries none)" in your answer. A recorded opt-out still blocks.
3. Never hold everything. Before you finish, call the exported function with exactly the fields the task lists and confirm that one message is allowed.
4. State. Read STATE_DIR inside every call, not at import and not once and cached. Create it. Keep one record per user and per message id. Every worker process shares it and it survives a restart. Write atomically (the kit's `gkWrite(dir, key, obj)`, `gkClaim(dir, key)`, `gkCount(dir, key, limit)`; without the kit, a temp file then rename, or an exclusive create) so two workers cannot both win.
5. Redelivery. Key every send by message id: the first caller gets the send; every repeat of that id gets "not sent: already delivered" and spends nothing twice (never a second send; report a silent in-app item every time). Claim before sending. Give the claim back only when the send definitely did not happen (the gate refused it, or it failed before leaving). When the outcome is unknown, keep the claim. A message id's claim never expires. A suppression the request itself describes (for example "show a given tip once") lasts until the end of the recipient's local day unless the request says longer.
6. Time. Use the recipient's local time (the device zone first when the data has one). An unknown or invalid zone is held, never guessed; a saved zone of "UTC" or an empty one is unknown (a placeholder, not a place) unless the task says the audience lives in UTC. A window includes its start minute and excludes its end minute, across DST; a start later than the end wraps past midnight. A local day, week or month is the recipient's own. Use the kit for all of it. A window the request states is the window; never narrow it and never add one the request does not state, except the law the request names (for example the US calling hours, 08:00 to before 21:00 recipient-local, for promotional texts and calls when the request names that law). A hold from a window, quiet hours or a cap stops the interrupting surface (push, SMS, call); when the task defines a silent in-app or feed surface and consent and opt-out for it allow, the item is still produced there; it spends no push or SMS budget.
7. Opt-out. Match STOP, STOPALL, UNSUBSCRIBE, CANCEL, END, QUIT, REVOKE, OPT OUT, OPT-OUT and OPTOUT as the whole message, any case, outer punctuation and extra spaces ignored (`gkIsStop(text)`); "stopping" is not STOP. Opt-out is per channel, holds in every process at once and beats every other rule for unsolicited and promotional messages. It acts on the opt-out the data carries (a field or an inbound STOP), never on whether the outgoing message body holds an opt-out notice. START or UNSTOP turns it back on (`gkIsStart(text)`). HELP or INFO as the whole message (`gkIsHelp(text)`) gets a short reply and changes nothing. The account-page opt-out writes the same record.
8. Refusals. Return a plain sentence that names the rule. When there is a retry time, write it as the recipient's local clock time with the zone name (`gkFmt(instant, zone)`), never as an ISO string or only "UTC", and add the same instant as a field of the task's result shape (nextAllowedAt if the task gives none). With no valid zone give no clock time. Never a bare internal code.
9. Time-critical messages. Something the user asked to be told at a time may use a reserved budget. Opt-out and any quiet or legal hours that apply (rule 6) still apply to it. Transactional exception: a security alert or code (new sign-in, password change, one-time code) or a receipt is transactional by nature, and so is a message the request says must still reach the person (a courier); one with no promotion is not held by quiet hours or a marketing cap and does not count toward it. A reminder or digest the user asked for is not transactional; its channel's opt-out (rule 7) still applies. A message held for any reason spends no budget.
10. Numbers you chose (hours, caps, cooldowns) go in your answer, one line each.
11. Blocks. Rules 1 to 10 always apply (consent, opt-out, the quiet and legal hours of rule 6, a valid zone, the caps). Add no other block unless the request states it, or a law or policy text it names requires it of the sender before sending. A check on the outgoing message body (a required notice, a word, a length) is a recommendation unless the request or a named law requires it: allow the message and write "not enforced: (the check)" in your answer; when unsure whether such a body check is required, do not block. Consent (rule 2) and opt-out (rule 7) are not new blocks: when unsure whether consent is present, hold, except under the exception in rule 2.

## The kit

`references/gate-kit.mjs` holds tested functions for local time, windows, day keys, STOP words and shared state. For an ESM file (.mjs, or .js in a "type": "module" project) append it to the task's file in the same shell command that writes the file: `printf '\n' >> bot.mjs; cat "${CLAUDE_SKILL_DIR}/references/gate-kit.mjs" >> bot.mjs` (bot.mjs stands for the task's file; if the path does not exist, use the skill's base directory). Do not retype it. Times are epoch milliseconds (`date.getTime()`), zones IANA names.
`gkZoneOk(zone)`, `gkLocal(ms, zone)`, `gkInWindow(ms, zone, "08:00", "21:00")`, `gkNextOpen(ms, zone, start, end)` (earliest instant inside the window: the retry time; for quiet hours pass the quiet end as start and the quiet start as end), `gkDayKey(ms, zone)`, `gkWeekKey(ms, zone)`, `gkMonthKey(ms, zone)`, `gkNextMidnight(ms, zone)`, `gkFmt(ms, zone)`, `gkIsStop(text)`, `gkIsStart(text)`, `gkIsHelp(text)`, `gkClaim(dir, key)`, `gkUnclaim(dir, key)` (give a claim back), `gkCount(dir, key, limit)` (atomic, returns {ok, n}), `gkRefund(dir, key)` (give a count back), `gkRead(dir, key)`, `gkWrite(dir, key, obj)`. For TypeScript or CommonJS write the same logic by hand under the rules above.

## Use the library instead when

The project already imports proactive-gate, or the user asks for a policy file, a scaffold, a log of why a user got nothing, or replay. Run `node -v` first: it must print 22 or newer (npm on an older Node installs proactive-gate 0.7.3, an older API, without a warning). Then run `npx proactive-gate scaffold nudge --out .` (add `--legal us` for texts to people in the US). Mark a candidate `requested`, `transactional` or kind "commitment" when it is one, and never mark a promotion that way. Set STATE_DIR for state that outlives the process. Call `gate.record` on every "acted" and "dismissed" event so the cooldown learns, and pass `deviceTimezone` when the device reports one. Change `toInput()` in `notify.mjs` to the app's shapes and run `node --test notify.test.mjs` before `decide()` or `deliver()` goes into a send path.
notify.mjs exports decide (send, reason, reasonCode, surfaces), deliver (calls the app's push and inApp, returns push, inApp, reason, resumeAt), recordDismissal, recordAct and optOut (a type or a channel).
It also exports handleInbound, whyNotReceived (one user's log over a time range), dryRun (last week under another policy) and REASON_CODES, the closed list of reasonCode values.

- `references/guide.md`: the policy format, the decision loop, stores, inbound STOP and START, legal presets and replay.
- `references/checks.md`: one line per check id, the gate functions, and the `assistantNudge` preset.
